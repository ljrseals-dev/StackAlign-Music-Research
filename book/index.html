Part I — Foundations

Chapter 1The Security Gap in Creative AI Systems

Creative software has a security problem that it rarely names. The problem is not that audio tools are uniquely vulnerable, or that language models introduce unprecedented attack surfaces—though both are true in specific ways. The problem is structural: the environments where creative work happens are assembled from components that were never designed to trust each other, and the security logic that binds them is almost always duplicated, improvised, or absent.

Consider a music production pipeline that uses an LLM to generate arrangement suggestions. The LLM runs in one process. The audio engine runs in another. A Python orchestration layer moves data between them. A configuration file controls routing. A plugin host loads third-party DSP code. An agent, perhaps, executes generated scripts to manipulate session state. Each component has its own notion of what a “safe” path looks like, what a “trusted” command is, and what “atomic” means. None of these notions are shared. The result is a system where the weakest interpretation of safety governs the whole.

This is the gap that StackAlign was built to address, and it is the gap this book explores across three domains: base server operation, LLM creation, and music production. The argument is not that StackAlign solves every problem in these domains. It is narrower and more useful: StackAlign provides a shared defensive foundation that these domains can consume without duplicating security logic, and the discipline of integrating it correctly is more valuable than the promise of any single security feature.

Static Review Is Not Runtime Clearance

The most important distinction in this book is between a defensive design that has been statically reviewed and a system that has been runtime-cleared. These are different states, and conflating them is the most common failure mode in security documentation for creative systems.

StackAlign-Baseline-Clean, in its current state, is a statically reviewed defensive design. Its architecture is documented. Its intended boundaries are articulated. Its execution model is defined around sa_exec, its path handling is designed around fixed canonical paths, and its persistence model is built around atomic writers and integrity hashes. These are real properties, and they matter.

But static review means exactly that: the design has been examined without runtime execution in a representative environment. Several concerns remain open. The K4 workstream—incomplete sa_exec caller migration and review—is the most concrete. There are residual review surfaces around history undo generation and config atomic writer callers. The root-apply chain has not been concretely established. And EL9 runtime apply remains untested.

These are not reasons to discard the baseline. They are reasons to integrate it carefully, with explicit gates, and to refuse the temptation to describe a promising defensive foundation as a finished security product. The audit’s actual boundary must travel with the baseline wherever it is integrated: this is a promising defensive baseline, not yet runtime-cleared. That sentence should appear in every consumer’s documentation until the gates in Chapter 11 are satisfied.

Why Creative Systems Duplicate Security Logic

The duplication problem is not a technical accident. It is an organizational one. Audio teams and ML teams and infrastructure teams often operate with different release cadences, different threat models, and different tolerances for latency. When a shared security primitive is perceived as slow, or awkward, or owned by another team, the path of least resistance is to reimplement it locally. A path-checking function gets copied. An execution wrapper gets rewritten. An atomic write pattern gets approximated with a rename that is almost atomic except on the filesystem that actually matters.

Each duplication is locally rational and globally corrosive. The copies drift. A fix applied to one does not reach the others. An audit that clears one surface does not clear the system. And the assumption that “the audio path is different” becomes a license to bypass the very controls that would have caught a traversal, an injection, or an interrupted write.

StackAlign’s integration contract exists to break this pattern. The baseline owns path safety, allowlisted execution through sa_exec, atomic file and configuration writes, integrity and hash verification, audit boundaries, and safe error contracts for rejected operations. Consumers own domain behavior only. They do not duplicate path-safety logic. They do not perform raw privileged execution outside sa_exec. They do not fork security helpers. They do not write directly, bypassing the atomic and integrity APIs.

This contract is deliberately asymmetric. It places the burden of correctness on a single foundation and the burden of discipline on every consumer. That asymmetry is the point. A shared foundation can be audited once. A duplicated control must be audited everywhere, and everywhere is where audits fail.

The Three Domains Are Not as Different as They Appear

It is tempting to treat server security, LLM training security, and audio production security as separate disciplines with separate toolchains. In practice, they share a common structure: each involves executing code, reading and writing files, managing configuration, and verifying the integrity of artifacts.

An LLM training run executes scripts, writes checkpoints, reads datasets, and loads configuration. A music production session executes plugins, reads and writes audio files, manages session configuration, and verifies rendered output. A base server executes services, reads and writes configuration and state, and verifies deployed artifacts. The surface-level details differ. The underlying security primitives are nearly identical.

This is why StackAlign can serve all three domains without becoming a monolith. It does not need to know what a checkpoint is or what a mix bus does. It needs to know how to execute a program safely, how to resolve a path canonically, how to write a file atomically, and how to verify that an artifact has not changed. These are domain-agnostic primitives. The domains supply the meaning; StackAlign supplies the boundary.

The dependency direction follows from this. StackAlign Baseline must not import product or model code. HUSH Core, Sculptor, Observatory, and Archive consume StackAlign. Agent infrastructure and LLM tooling consume StackAlign. The arrow points upward, never downward. When the arrow is reversed—when a security primitive imports domain logic, or when a domain silently reimplements a primitive—the foundation stops being a foundation and becomes another component with its own assumptions.

What This Book Does Not Claim

This book does not claim that StackAlign provides a neural network architecture, a tokenizer, a dataset, training weights, a GPU training engine, an optimizer, or LLM reasoning and inference capabilities. Those must be provided by the actual model stack. StackAlign hardens the environment around model creation; it does not create the model.

This book does not claim that StackAlign secures audio processing in a way that makes latency disappear. Security checks have costs, and real-time audio has hard deadlines. The claim is that audio processing cannot bypass sa_exec or the atomic writer simply because it is latency-sensitive. The correct response to latency pressure is to design the boundary so that checks happen at the right points, not to remove the boundary.

And this book does not claim that static review is sufficient. Every integration path described here terminates in runtime validation on a disposable EL9 environment, with an evidence bundle that records what was tested, what failed, and what remains unresolved. Until that evidence exists, the honest description of StackAlign is a promising defensive baseline, not a cleared runtime dependency.

The chapters that follow build the case domain by domain. Part II establishes StackAlign as a base server: its topology, its execution governance, and its persistence and integrity model. Part III applies the same foundation to LLM creation, treating training orchestration, dataset boundaries, checkpoint integrity, and safe inference as governed workloads rather than special cases. Part IV turns to music production, where HUSH Core, HUSH Processor, Sculptor, Observatory, and Archive consume the baseline without duplicating its logic. Part V closes with the operational discipline—disposable EL9 validation, evidence collection, consumer manifests, and version pinning—that separates a promising design from an integration-ready system.

The through-line is simple: a shared defensive foundation is only as strong as the discipline of its consumers, and that discipline is expressed in what they refuse to duplicate, what they refuse to bypass, and what they refuse to claim before the evidence exists.

Chapter 2StackAlign Baseline — Architecture and Boundaries

StackAlign is easiest to understand as a set of refusals. It refuses to be an audio plugin. It refuses to be a model trainer. It refuses to absorb domain logic. It refuses to claim runtime clearance before runtime evidence exists. What remains after these refusals is a compact set of defensive primitives that can be consumed by systems that do have domain purposes: HUSH Core and its siblings in audio, model-creation tooling in the LLM domain, and shared agent infrastructure across both.

The Four Primitives

The baseline’s architecture rests on four primitives: fixed path safety, allowlisted execution through sa_exec, atomic file and configuration writes, and integrity verification through hashes. Each primitive is deliberately narrow, and each is designed to be consumed rather than extended.

Fixed path safety means that paths are resolved canonically and constrained to known roots. The design intent is to reject traversal and ambiguity before any file operation occurs. This is not a novel idea; it is a foundational one that is routinely implemented incorrectly when each consumer writes its own version. The baseline centralizes it so that the canonicalization rules, the root constraints, and the rejection behavior are defined once.

Allowlisted execution through sa_exec means that privileged execution does not happen through raw process invocation scattered across a codebase. It happens through a single interface that consults an allowlist, applies the path-safety rules, and returns a safe error contract when an operation is rejected. The value of sa_exec is not that it makes execution safe in some absolute sense. The value is that it makes execution governable: there is one place to review, one place to audit, and one place to fix.

Atomic file and configuration writes mean that a write either completes or leaves the prior state intact. The design intent is to survive interruption, rollback, and concurrent access without leaving partial state that later operations misinterpret. Atomicity is not a property that can be bolted on after the fact; it has to be designed into the write path.

Integrity verification through hashes means that artifacts and configuration can be checked against expected values before use. This is the primitive that lets a consumer answer the question “is this the file I think it is?” without trusting the filesystem, the network, or the build pipeline.

These four primitives compose. Path safety constrains where an operation can occur. sa_exec governs whether it can occur. Atomic writes ensure that the result is either complete or absent. Integrity verification ensures that what was written or loaded is what was intended. A system that has all four has a coherent defensive posture. A system that has three has a gap.

What the Integration Contract Owns

The integration contract is the mechanism that prevents the four primitives from being reimplemented downstream. It is worth restating precisely because the temptation to fork is strongest when a consumer believes its domain is special.

StackAlign owns fixed and canonical path safety. It owns allowlisted execution via sa_exec. It owns atomic file and configuration writes. It owns integrity and hash verification. It owns audit and event boundaries. It owns safe error contracts for rejected operations.

Consumers own domain behavior only. They do not duplicate path-safety logic. They do not perform raw privileged execution outside sa_exec. They do not fork security helpers. They do not write directly, bypassing the atomic and integrity APIs.

This contract is not a suggestion. It is the condition under which the baseline remains auditable. Every fork of a security helper creates a new surface that must be audited separately. Every raw execution path creates a new place where the allowlist can be circumvented. Every direct write creates a new opportunity for partial state. The contract exists to keep the number of auditable surfaces small enough that auditing is possible.

The Dependency Direction

The dependency direction is a single upward arrow: StackAlign Baseline sits at the bottom, and every consumer sits above it. HUSH Core, Sculptor, Observatory, and Archive consume StackAlign. Agent infrastructure and LLM tooling consume StackAlign. StackAlign must not import product or model code.

This direction is not merely architectural hygiene. It is a security property. If StackAlign imports product code, then a vulnerability in product code becomes a vulnerability in the foundation, and the foundation can no longer be audited independently. If a product imports another product’s security logic, then the foundation is bypassed and the duplication problem returns. The arrow must point one way.

In practice, the dependency direction is enforced by packaging and review. A consumer declares a pinned dependency on a StackAlign tag. A change that would add a reverse dependency is rejected at review. A consumer that needs a primitive StackAlign does not provide is expected to articulate the need and, if the primitive is genuinely domain-agnostic, contribute it upstream—not to fork it locally.

The K4 Problem

The most concrete open concern in the baseline is K4: incomplete sa_exec caller migration and review. This is the workstream that determines whether the allowlisted execution primitive is actually governing all the execution paths that matter, or whether some callers still bypass it or reach privileged execution through paths that have not been reviewed.

K4 is not a design flaw. It is an incomplete migration, which is a different and more tractable problem. The design says execution goes through sa_exec. The migration asks: does it, everywhere? And where it does, is the caller’s reachability to privileged execution understood and bounded?

The residual review surfaces compound this. History undo generation is a surface where prior state is reconstructed and applied; if the reconstruction or the application path can reach privileged execution or bypass path safety, the baseline’s guarantees do not hold for that surface. Config atomic writer callers are a surface where the atomicity primitive is invoked; if some callers write configuration directly or approximate atomicity incorrectly, the persistence guarantees are partial.

And the root-apply chain has not been concretely established. This is the most serious of the open items because it concerns the path by which changes are applied at elevated privilege. If that chain is not concretely established, then the claim that sa_exec governs privileged execution is a design intent rather than a verified property. The honest position is to treat the root-apply chain as unresolved until the chain is mapped, reviewed, and validated.

Why the Baseline Is Still Worth Integrating

A reader might reasonably ask why a baseline with open K4 work, residual review surfaces, and an unresolved root-apply chain should be integrated at all. The answer is that the alternative—duplicated, improvised security logic across audio tools, model-creation tooling, and agent infrastructure—is worse, and the open items are tractable.

The baseline provides a single place to close K4. It provides a single place to review history undo and config atomic writer callers. It provides a single place to establish the root-apply chain. A consumer that forks the primitives instead gets its own K4, its own residual surfaces, and its own unresolved chains, multiplied across every product. Centralizing the problem does not solve it, but it makes solving it possible.

The integration strategy follows from this. StackAlign is integrated as a shared defensive foundation, not as an audio plugin or a model trainer. HUSH Core consumes it as a foundation consumer. Sculptor consumes it to protect file and config operations and tool invocation. Observatory consumes it for safe inspection, analysis, and diagnostic workflows. Archive consumes it for integrity, safe persistence, and recovery. LLM model creation consumes it as a separate integration to harden training orchestration, tooling, and artifact management. Agent infrastructure consumes it as a shared consumer to govern tool execution and changes.

The Security Status That Travels with the Baseline

The baseline’s current security status should travel with it anywhere it is integrated. That status is: static review only, runtime clearance pending. Defensive design is documented and statically reviewed. sa_exec migration (K4) is still open. History undo generation and config atomic writer callers are residual review surfaces. The root-apply chain is not concretely established. EL9 runtime apply is untested.

This status is not a disclaimer to be buried in a README. It is an operational fact that determines what a consumer may claim. A consumer may claim that it inherits a statically reviewed defensive design. It may not claim runtime security clearance until the gates in Chapter 11 are satisfied. The distinction matters because the most dangerous outcome is not an insecure system; it is a system that believes it is secure because a design document said so.

The architecture of StackAlign is therefore both a set of primitives and a set of honest boundaries. The primitives—path safety, sa_exec, atomic writes, integrity verification—are the foundation. The boundaries—what StackAlign owns, what consumers own, which direction dependencies point, and what status the baseline carries—are what keep the foundation from being misrepresented. A foundation that is overclaimed is worse than a foundation that is honestly incomplete, because the overclaim removes the pressure to finish the work.

Part II — StackAlign as Base Server

Chapter 3Server Topology and Execution Governance

StackAlign as a base server is not a single deployment. It is a role that the baseline plays in relation to consumers, and the topology of those consumers determines where the security boundaries actually fall. This chapter maps that topology and then examines how sa_exec governs execution across it.

The Server as a Shared Foundation

The most important topological decision is that StackAlign is a shared foundation, not a server product. It does not listen on a port. It does not expose an API to end users. It does not own a database. It is a library and a set of conventions that consumers link against and call into.

This matters because the alternative—turning the baseline into a server—would create a new attack surface and a new set of availability requirements that the baseline was not designed to meet. A server must handle authentication, rate limiting, request parsing, and all the other concerns of a network-facing service. StackAlign’s primitives are not these concerns. Making it a server would dilute its focus and expand its audit surface.

As a shared foundation, StackAlign sits beneath a set of consumer roles. HUSH Core is a foundation consumer: it applies defensive boundaries to audio-side tools. Sculptor is a consumer that protects file and config operations and tool invocation. Observatory is a consumer for safe inspection, analysis, and diagnostic workflows. Archive is a consumer for integrity, safe persistence, and recovery. Agent infrastructure is a shared consumer that safely governs agent tool execution and changes. LLM model creation is a separate integration that hardens training orchestration, tooling, and artifact management.

Each of these roles consumes the same primitives. None of them owns a private copy. The topology is a star with StackAlign at the center, not a mesh with security logic distributed across every node.

Execution Governance Through sa_exec

Execution is where topology becomes concrete. Every consumer that executes a program—whether it is an audio tool, a training script, a diagnostic command, or an agent-generated action—must route that execution through sa_exec. The primitive is the single point at which the allowlist is consulted, path safety is applied, and a safe error contract is returned on rejection.

The governance model has three layers. The first layer is the allowlist: a declared set of programs and operations that are permitted. The second layer is the path constraint: the canonical resolution and root confinement that determines whether the program and its arguments refer to permitted locations. The third layer is the error contract: a defined behavior when an operation is rejected, so that consumers handle rejection consistently rather than falling back to raw execution.

The value of centralizing these layers is that they can be reviewed once. In a distributed model, each consumer would implement its own allowlist, its own path constraint, and its own rejection behavior. The allowlists would drift. The path constraints would disagree on edge cases. The rejection behaviors would range from clean failure to silent fallback. Centralization does not eliminate the possibility of error, but it makes the error auditable in one place.

The governance model also defines what sa_exec does not do. It does not sandbox the executed program. It does not guarantee that the program’s behavior is safe. It does not replace operating-system controls, container isolation, or privilege separation. It governs invocation: which programs can be invoked, with which paths, under which rejection behavior. This is a narrower guarantee than sandboxing, and it is a more honest one. A consumer that needs sandboxing must provide it at the operating-system or container layer; sa_exec ensures that the invocation path is governed and reviewable.

Privileged Execution and the Root-Apply Chain

The most sensitive execution path is privileged execution: the operations that run with elevated rights. The baseline’s design intent is that privileged execution is reached only through sa_exec, and that the chain from a consumer call to a privileged operation is concrete and reviewable.

That chain is not yet concretely established. This is the open root-apply concern, and it is the item that most directly limits what the server topology can claim. The topology can claim that consumers route execution through sa_exec. It cannot yet claim that every privileged operation is reachable only through a reviewed chain, because the chain itself has not been mapped.

The correct posture is to treat the root-apply chain as a first-class deliverable of the server integration. The chain should be mapped from each privileged operation backward to its callers, and forward from sa_exec to the operations it can reach. The map should identify every point at which elevation occurs, every input that influences the elevated operation, and every path-safety and allowlist check that applies. Until that map exists and has been reviewed, privileged execution is a design intent rather than a verified property.

This does not mean privileged operations should be avoided. It means they should be instrumented and reviewed before the server claims governance over them. A chain that is mapped is a chain that can be defended. A chain that is assumed is a chain that can be bypassed without anyone noticing.

Topology and the Prevention of Security-Logic Forks

The star topology has a second purpose beyond centralizing review: it prevents security-logic forks. In a mesh topology, where each consumer connects to every other consumer, it is natural for one consumer to reuse another’s security helper. The reuse looks efficient, but it creates a hidden dependency and a hidden audit surface. If the helper changes, the consumers that depend on it change. If the helper is insecure, the consumers inherit the insecurity without knowing it.

In the star topology, consumers connect to StackAlign and to each other only through domain interfaces, not through security helpers. A consumer that needs path safety calls StackAlign. It does not call another consumer’s path-safety function. A consumer that needs atomic writes calls StackAlign. It does not borrow another consumer’s writer.

This discipline is enforced by the integration contract and by review. A pull request that adds a cross-consumer security dependency is rejected. A pull request that duplicates a primitive is rejected or redirected upstream. The topology is not just a diagram; it is a review rule.

Server Roles and Their Boundaries

The consumer roles can be described in terms of the boundary each one places around its domain.

HUSH Core is the foundation consumer for audio. Its boundary is the audio tool execution surface and the file and configuration operations that audio tools depend on. It does not own a private path-safety implementation. It does not execute audio tools outside sa_exec. It does not write configuration outside the atomic writer.

Sculptor’s boundary is file and configuration operations and tool invocation. It is the consumer that most directly exercises the path-safety and atomic-write primitives. Its integration should be reviewed for direct writes and raw execution, because those are the failure modes that the baseline exists to prevent.

Observatory’s boundary is safe inspection, analysis, and diagnostic workflows. Its characteristic risk is read-path traversal and unintended write side effects during diagnostics. It consumes path safety for reads and atomic writes for any diagnostic artifacts it produces.

Archive’s boundary is integrity, safe persistence, and recovery. It is the consumer that most directly exercises the integrity-verification primitive. Its recovery paths are the place where history undo generation and interrupted-write behavior matter most, and they should be reviewed against the residual review surfaces identified in the baseline audit.

Agent infrastructure’s boundary is governed tool execution and changes. It is the consumer where the allowlist is most exposed to untrusted input, because agent-generated actions are, by definition, not fully predictable. The sa_exec governance model is the primary defense here, and the review should focus on whether every agent-initiated execution routes through it.

LLM model creation’s boundary is training orchestration, tooling, and artifact management. It is a separate integration rather than a HUSH consumer, but it uses the same primitives. Its characteristic risk is the execution of training scripts and the handling of checkpoints and datasets, which are addressed in Part III.

What the Server Topology Does Not Provide

The server topology does not provide network security, authentication, authorization, or tenant isolation. Those are properties of the deployment environment, not of StackAlign. A server that uses StackAlign still needs a network boundary, an identity system, and a container or virtual-machine isolation model. StackAlign hardens the execution and persistence surfaces within the server; it does not replace the server’s other security layers.

The topology also does not provide high availability, failover, or disaster recovery. Atomic writes and integrity verification support recovery, but they do not constitute a recovery plan. Archive’s recovery behavior is a consumer responsibility that uses the baseline’s primitives; it is not a baseline feature.

And the topology does not provide runtime clearance. The star topology with StackAlign at the center is a design that can be cleared. It is not a design that has been cleared. The distinction returns in every chapter because it is the distinction that keeps the integration honest.

Chapter 4Path Safety, Atomic Persistence, and Integrity

The primitives that matter most in day-to-day operation are the least glamorous: resolving a path correctly, writing a file without leaving partial state, and checking that an artifact is what it claims to be. This chapter examines each primitive in the context of server operation and identifies the residual review surfaces that remain open.

Path Safety Beyond the Obvious Cases

Path traversal is the canonical case: an input containing ../ escapes a confined root. But the interesting failures are the ones that traversal checks miss. Symbolic links can redirect a canonical path after the check. Case-insensitive filesystems can make two different strings resolve to the same file. Unicode normalization can make visually identical paths distinct. A path that is absolute on one platform and relative on another can change meaning when configuration is shared.

StackAlign’s fixed path safety is designed to resolve paths canonically and constrain them to known roots before any operation occurs. The design intent is to make the resolution rules explicit and central, so that every consumer applies the same rules. The open question is whether every caller uses the primitive, and whether the primitive’s canonicalization covers the edge cases that the deployment environment actually presents.

The residual review surface around history undo generation is relevant here. History undo reconstructs prior state and applies it. If the reconstruction derives paths from stored history rather than from current configuration, and if those paths are not re-canonicalized and re-confined before application, the undo path can become a traversal vector. The review should ask: are history-derived paths treated as untrusted input? Are they resolved through the same primitive as live input? Is the root confinement applied at application time, not only at storage time?

The same question applies to config atomic writer callers. If a caller passes a path to the atomic writer without first resolving it through the path-safety primitive, the writer’s atomicity guarantee is intact but the path-confinement guarantee is bypassed. The review should ask: does every atomic-writer caller resolve its path through the primitive, or do some callers rely on the writer to do it?

Atomic Writes and the Meaning of “Complete”

Atomicity is often described as “all or nothing,” but the useful definition is narrower: after an interruption, a reader sees either the prior state or the new state, never a partial state. Achieving this requires a write protocol, not just a single system call. A common pattern is to write to a temporary file in the same directory, flush and sync, and then rename over the target. The rename is atomic on many filesystems, but the protocol around it determines whether the guarantee holds.

The baseline’s atomic file and configuration writes are designed to provide this guarantee. The residual review surface is whether every caller uses the protocol correctly. A caller that writes directly to the target and then renames is not atomic. A caller that writes to a temporary file in a different directory may fail the rename across filesystems. A caller that does not sync before rename may lose the new state on power failure while the old state is already gone.

The review of config atomic writer callers is therefore not a formality. It is the difference between a persistence layer that survives interruption and one that merely looks like it does. The review should enumerate every caller, classify the write pattern, and verify that the pattern matches the protocol. Callers that deviate should be corrected or explicitly documented as exceptions with their own recovery behavior.

Integrity Verification and the Trust Boundary

Integrity verification answers a deceptively simple question: is this artifact the one that was intended? A hash comparison is straightforward when the expected value is known and trusted. The difficulty is in the trust boundary around the expected value.

If the expected hash is stored alongside the artifact, and both can be modified by the same actor, the verification provides no protection against that actor. If the expected hash is fetched over the network without authentication, the verification is only as trustworthy as the network. If the expected hash is embedded in a build artifact that itself is not verified, the chain of trust is broken at the root.

StackAlign’s integrity primitive provides the comparison mechanism. It does not, by itself, establish the trust boundary for the expected values. That is a consumer responsibility. Archive, as the integrity consumer, must define where expected hashes come from and why they are trusted. LLM model creation must define the same for checkpoints and model artifacts. The baseline provides the mechanism; the consumer provides the trust model.

This division is important because it prevents a common overclaim. A system that computes hashes and compares them is not automatically secure. It is secure only if the expected values are trusted. The baseline’s documentation should state this explicitly, and consumers should document their trust model for expected hashes as part of their integration.

The Interaction Between Primitives

The primitives are most valuable when they compose. Path safety confines an operation to a root. The atomic writer ensures the write is complete or absent. Integrity verification confirms the result. An operation that uses all three has a defensible posture: it cannot escape the root, it cannot leave partial state, and its result can be checked.

An operation that uses only two has a gap. Path safety without atomicity can write a confined but partial file. Atomicity without path safety can write a complete file to an unintended location. Integrity without path safety can verify a file that should never have been read. The review of any consumer should therefore ask not only whether each primitive is used, but whether the primitives are composed on the paths that matter.

The history undo and config atomic writer surfaces are exactly the places where composition is most likely to break. History undo may apply a path that was safe at storage time but is not safe at application time. Config atomic writers may be called with paths that were resolved by a different code path. The review should trace composition, not just individual primitive usage.

The Root-Apply Chain as a Persistence Concern

The root-apply chain is usually discussed as an execution concern, but it is also a persistence concern. Applying changes at elevated privilege often involves writing configuration, replacing files, and updating state. If those writes bypass the atomic writer, the elevated operation can leave the system in a partial state that is difficult to recover from precisely because it occurred at elevated privilege.

Establishing the root-apply chain concretely therefore requires mapping both the execution path and the persistence path. For each elevated operation, the map should identify what is written, through which writer, with which path resolution, and with what recovery behavior if the write is interrupted. A chain that is mapped only for execution is half-mapped.

The Status of These Primitives Today

The path-safety, atomic-write, and integrity primitives are designed and statically reviewed. They are not runtime-cleared. The residual review surfaces—history undo generation and config atomic writer callers—are open. The root-apply chain is not concretely established. These are the specific items that the validation work in Chapter 11 must address before the server integration can be described as runtime-validated.

The honest summary is that the primitives are a sound design with an incomplete migration and an incomplete review. That is a normal state for a defensive foundation that is being integrated into real systems. It is not a state that supports a claim of runtime clearance, and it is not a state that justifies bypassing the primitives because they are “not finished.” The correct response is to close the open items, not to route around them.

Part III — LLM Creation on StackAlign

Chapter 5Training Orchestration as a Governed Workload

LLM creation is where the temptation to treat security as someone else’s problem is strongest. Training is computationally expensive, the model architecture is complex, and the security concerns feel distant from the mathematics. But training is also a workload: it executes scripts, reads datasets, writes checkpoints, and loads configuration. Those are exactly the surfaces StackAlign governs. The goal is not to secure the model’s reasoning. The goal is to secure the environment in which the model is created.

What StackAlign Does Not Provide

The boundary must be stated first because it is the most frequently violated. StackAlign does not provide a neural network architecture, a tokenizer, a dataset, training weights, a GPU training engine, an optimizer, or LLM reasoning and inference capabilities. Those must be provided by the actual model stack.

StackAlign hardens the environment around model creation. It governs the execution of training scripts and tooling, the handling of model configuration and checkpoint files, the boundaries of dataset workspaces, the integrity of model artifacts, the atomicity of configuration and checkpoint metadata writes, and the orchestration of build, training, and evaluation tasks. These are infrastructure concerns, and they are separable from the model’s mathematical and architectural concerns.

This separation is not a limitation. It is what makes the integration tractable. A security foundation that tried to understand the model would be coupled to a fast-moving domain and would require re-auditing on every architectural change. A security foundation that governs execution, paths, writes, and integrity is stable across architectural changes because those concerns do not change when the model does.

Training Scripts as Governed Execution

A training run begins with a script. That script may be a shell wrapper, a Python entry point, a distributed launcher, or an agent-generated orchestration step. Each of these is an execution path, and each should route through sa_exec.

The governance model applies the same three layers described in Chapter 3. The allowlist declares which training scripts and launchers are permitted. The path constraint ensures that the script and its working directory are confined to the training workspace. The error contract ensures that a rejected execution fails cleanly rather than falling back to raw invocation.

The characteristic failure in training orchestration is the “temporary” bypass. A launcher needs to run a helper that is not on the allowlist. A distributed job needs to invoke a binary in a location outside the workspace. A debugging script needs raw execution to reproduce an issue. Each bypass is locally justified and collectively corrosive. The integration contract exists to make the bypass visible: if a training orchestration step needs an execution that sa_exec does not permit, the correct response is to extend the allowlist through review, not to route around the primitive.

Dataset Workspace Boundaries

Datasets are large, often shared, and frequently mounted from external storage. The path-safety primitive is the primary defense for dataset access: reads and writes are confined to declared workspace roots, and paths are canonically resolved before access.

The subtlety is that training often needs to read from multiple roots—a dataset mount, a cache directory, a configuration directory, a checkpoint directory. Each root should be declared, and the path-safety rules should enforce that an operation stays within the union of declared roots. A read that escapes the union is a traversal, even if it is “just” reading a system file, because the escape itself is the signal that something is wrong.

Dataset workspace boundaries also matter for writes. Training jobs often write logs, metrics, and intermediate artifacts. If those writes bypass the atomic writer or escape the workspace, the training run can corrupt shared state or leave partial artifacts that later runs misinterpret. The discipline is the same as in server operation: no direct writes, no path joins without canonical resolution, no exceptions for “just logs.”

Checkpoint Integrity

Checkpoints are the most valuable artifacts a training run produces. They are also the most tempting to write with ad hoc code, because checkpoint formats vary and performance pressure is high. The result is often a write path that is almost atomic, almost verified, and almost confined.

The baseline’s contribution is to make the checkpoint write path explicit. Checkpoint metadata and configuration writes should use the atomic writer. Checkpoint artifacts should be hashed and the hash recorded through the integrity primitive. The expected hash should be stored in a location whose trust model is documented. The checkpoint directory should be a declared workspace root, and the path should be resolved through the path-safety primitive before the write.

None of this secures the checkpoint against a malicious actor who can modify both the checkpoint and its expected hash. That is a trust-model problem, and it belongs to the consumer. The baseline provides the mechanism for detecting change; the consumer provides the trust anchor. The integration is honest only if both are documented.

Artifact Management and the Build-to-Training Handoff

Training is rarely a single step. It involves a build phase that produces containers or environments, a data phase that prepares datasets, a training phase that produces checkpoints, and an evaluation phase that selects among them. Each handoff is a place where integrity can be lost.

StackAlign’s integrity primitive can be applied at each handoff: the build artifact is hashed, the dataset snapshot is hashed, the checkpoint is hashed, the evaluation result is hashed. The hashes form a chain that makes it possible to ask, after the fact, which exact inputs produced which exact outputs. This is not a security guarantee in itself, but it is a prerequisite for one, because it makes tampering detectable and accidental corruption visible.

The atomic-write primitive supports the handoff by ensuring that an artifact is either fully present or absent when the next phase begins. A training job that starts on a partially written dataset is a job whose results are not reproducible, and reproducibility is the foundation of any meaningful evaluation.

Agent-Generated Training Code

The most delicate case is agent-generated training code: an LLM or agent writes a script, and the orchestration layer executes it. This is increasingly common in model-development workflows, and it concentrates risk because the code is not human-reviewed before execution.

The sa_exec allowlist is the primary defense. The agent’s execution surface should be restricted to a declared set of interpreters and tools, with path confinement to a sandbox workspace. The agent should not be able to invoke arbitrary binaries, and it should not be able to escape the workspace through path manipulation. The error contract should be strict: a rejected execution fails, and the agent receives a clear rejection rather than a silent fallback.

This does not make agent-generated code safe in general. It makes the execution boundary governable. The agent can still write harmful code within the permitted surface, and the defense against that is review, testing, and sandboxing at layers the baseline does not provide. The baseline ensures that the agent’s code cannot bypass the execution governance to reach surfaces it was never granted.

The Separation That Makes the Integration Work

The separation between model concerns and infrastructure concerns is what allows StackAlign to be a stable foundation for LLM creation. The model stack changes: architectures evolve, optimizers are replaced, tokenizers are redesigned, training objectives shift. The infrastructure concerns—execution governance, path safety, atomic writes, integrity verification—remain the same.

A consumer that respects this separation gets a security foundation that does not need to be re-audited when the model changes. A consumer that violates it—by embedding model-specific security logic in the foundation, or by bypassing the foundation because the model stack “needs” raw access—recreates the duplication problem and loses the auditability that justified the integration.

The correct architecture places StackAlign beneath the training orchestration layer, with the orchestration layer consuming the primitives and the model stack consuming the orchestration layer. The arrow points one way: StackAlign does not import model code, and the model code does not reimplement StackAlign’s primitives.

Chapter 6Dataset Boundaries and Checkpoint Integrity

This chapter extends the training-orchestration argument into two specific surfaces: dataset workspaces and checkpoint artifacts. Both are high-value, both are frequently handled with ad hoc code, and both benefit disproportionately from the baseline’s primitives.

Dataset Workspaces as Security Boundaries

A dataset workspace is a declared root within which dataset reads and writes are permitted. The declaration matters because it converts an implicit assumption (“the training job will only read the dataset”) into an enforceable boundary (“an operation that resolves outside the declared roots is rejected”).

The boundary should be defined at the start of the training pipeline and enforced at every access. A read of a dataset shard resolves the path through the path-safety primitive and checks that the resolved path is within the declared roots. A write of a prepared dataset or a cache artifact follows the same rule. The check should happen on the canonical path, after resolution, not on the input string.

The characteristic failure is the convenience exception: a training job needs to read a tokenizer file from the model repository, or a configuration file from a shared location, and the path is outside the declared dataset roots. The exception is added, the boundary weakens, and the next exception is easier. The disciplined response is to declare the additional root explicitly and review the declaration, rather than to add a one-off bypass.

Checkpoint Writes and Atomicity Under Performance Pressure

Checkpoint writes happen under performance pressure. A training job may write a checkpoint every few hundred steps, and the write may be large. The pressure to use a fast, non-atomic write is real.

The baseline’s position is that checkpoint metadata and configuration should use the atomic writer, and checkpoint artifacts should be written through a protocol that provides the same all-or-nothing visibility. The performance cost is a design consideration: the protocol should be efficient, but efficiency is not a reason to abandon atomicity. A checkpoint that is corrupted by an interrupted write is worse than a checkpoint that took slightly longer to produce, because the corrupted checkpoint may be loaded by a later run that has no way to detect the corruption.

Integrity verification addresses the detection gap. A checkpoint that is hashed at write time and verified at load time can be rejected if it is incomplete or corrupted. The combination of atomic writes and integrity verification gives the training pipeline a checkpoint that is either valid or rejected, rather than a checkpoint that is silently wrong.

The Trust Anchor Problem

Integrity verification is only as strong as the trust anchor for the expected hash. If the expected hash is stored in the same writable location as the checkpoint, an actor who can modify the checkpoint can modify the hash. The verification then confirms consistency, not integrity.

The trust anchor must be defined by the consumer. Options include storing expected hashes in a separate, write-protected location; signing the hashes with a key that the training job does not possess; or recording them in an append-only log that is reviewed before loading. Each option has costs and tradeoffs, and the choice depends on the threat model.

StackAlign does not choose the trust anchor. It provides the comparison mechanism and the atomic-write and path-safety primitives that support a trustworthy anchor. The consumer’s documentation should state the anchor explicitly, because a verification mechanism without a stated anchor is a claim without a basis.

Dataset Provenance and the Integrity Chain

Dataset integrity is not only about detecting corruption. It is also about provenance: which dataset version, prepared by which pipeline, with which transformations, produced this training run. A hash chain across the dataset snapshot, the preparation code, and the training configuration makes provenance auditable.

The baseline’s integrity primitive supports this chain by making each artifact hashable and each hash recordable. The consumer’s responsibility is to define the chain and to record it in a way that can be reconstructed. A training run that cannot answer “which data produced this checkpoint?” is a run whose results cannot be defended, regardless of how secure its execution surface is.

The Interaction with Model Artifacts

Checkpoints become model artifacts when they are selected for inference or packaging. At that transition, the integrity chain must be preserved. The selected checkpoint’s hash should be verified against the recorded value, and the verification result should be recorded as part of the artifact metadata.

If the transition involves conversion—for example, converting a training checkpoint to an inference format—the converted artifact should be hashed and the relationship to the source checkpoint recorded. The chain should be unbroken from dataset to inference artifact, so that a question about the inference artifact can be answered by tracing back through the chain.

This is more than good hygiene. It is the foundation of any claim that an inference system is using the model it says it is using. Without the chain, the claim rests on trust in the filesystem and the deployment process. With the chain, the claim rests on verifiable hashes.

Review Surfaces Specific to Dataset and Checkpoint Handling

The dataset and checkpoint surfaces add specific review questions beyond the baseline’s general residual surfaces.

For datasets: are all roots declared? Are canonical paths checked after resolution? Are writes confined to the workspace? Are preparation scripts executed through sa_exec? Is the dataset snapshot hashed and recorded?

For checkpoints: are metadata and configuration written through the atomic writer? Is the checkpoint artifact written through an all-or-nothing protocol? Is the expected hash stored under a documented trust anchor? Is the hash verified at load time? Is the chain from dataset to checkpoint to artifact preserved?

These questions are the practical form of the integration contract in the LLM domain. A training pipeline that can answer them has a defensible dataset and checkpoint posture. A pipeline that cannot answer them has an undocumented risk surface, regardless of how the model performs.

The Boundary Between Infrastructure and Model

The recurring temptation in dataset and checkpoint handling is to let model-specific logic into the security layer. A checkpoint format may be complex; it is tempting to write a custom checkpoint writer inside the orchestration layer and to treat that writer as part of the security boundary. A dataset may have a specialized index; it is tempting to write a custom path resolver for the index.

Each of these temptations blurs the boundary. The security layer should not know about checkpoint formats or dataset indexes. It should know about paths, writes, and hashes. The model-specific logic belongs in the orchestration layer, which consumes the security primitives rather than reimplementing them.

The discipline is to keep the primitives domain-agnostic and to let the domain logic compose them. A checkpoint writer that uses the atomic writer and the integrity primitive is a domain component that consumes the foundation. A checkpoint writer that implements its own atomicity is a fork, and every fork is a new audit surface.

Chapter 7Safe Inference and Agent Tooling

Inference is where the model meets the world. It is also where security claims are most likely to overreach. The temptation is to say that a safe inference environment makes the model safe. It does not. The environment can be governed; the model’s reasoning cannot be guaranteed by the environment. This chapter draws that boundary precisely and then applies the baseline to the surfaces that can be governed.

Artifact Verification Before Loading

The first inference security question is not about the model’s behavior. It is about whether the artifact being loaded is the artifact that was intended. A model that loads a tampered checkpoint can produce outputs that are wrong in ways no amount of inference-time monitoring will detect, because the monitoring is calibrated against the intended model.

The integrity primitive addresses this. Before loading, the model artifact’s hash is computed and compared against the expected value from the documented trust anchor. If the verification fails, loading is rejected. The rejection should be explicit and should not fall back to an unverified artifact.

The verification should cover not only the primary weights but also tokenizer files, configuration files, and any auxiliary artifacts that affect inference behavior. A model whose weights are verified but whose tokenizer is not is a model whose behavior can be changed without detection. The artifact set should be defined, and each member should be verified.

The Inference Environment as a Governed Surface

The inference process itself is an execution. It should route through sa_exec if it is launched as a subprocess, and its file access should be confined to declared roots through the path-safety primitive. The model directory, the input directory, and the output directory should be declared, and access outside those roots should be rejected.

The characteristic inference-time bypass is the dynamic load: a model loads a plugin or a custom operator from a path that was not declared. The load succeeds because the path was not checked, and the inference environment now executes code that was outside the governance model. The disciplined response is to declare loadable components as part of the artifact set and to verify them before loading, rather than to allow dynamic loads from arbitrary paths.

Inference Security Is Not Model Intelligence

The boundary must be stated clearly: securing the inference environment does not secure the model’s reasoning. A verified artifact can still produce harmful, biased, or incorrect outputs. A governed execution surface can still execute a model that has been trained on problematic data. A confined path can still point to a model whose behavior is undesirable.

The environment controls what the model can access and what can access the model. It does not control what the model says. Output filtering, content moderation, red-teaming, and evaluation are separate disciplines that operate on the model’s behavior. They are necessary, and they are not provided by StackAlign.

This distinction matters because conflating environmental security with model safety leads to overclaim. A deployment that says “our inference is secure” may mean that the artifact is verified and the execution is governed. It should not be understood to mean that the model’s outputs are safe. The documentation should separate the two claims.

Agent Tooling as a Governed Execution Surface

Agent infrastructure is the consumer where execution governance matters most, because the agent’s actions are generated rather than predetermined. An agent may decide to run a shell command, call a tool, modify a file, or invoke another agent. Each of these is an execution, and each should route through sa_exec.

The allowlist for agent tooling should be explicit and minimal. It should declare which tools the agent can invoke, with which argument patterns, and within which paths. The error contract should be strict: an unpermitted invocation is rejected, and the agent receives a clear rejection that it can reason about. Silent fallback—where a rejected invocation is retried through a different path—defeats the governance model.

The path constraints should confine the agent’s file operations to a declared workspace. An agent that can read or write outside its workspace is an agent whose blast radius is unbounded. The path-safety primitive should enforce the confinement on every operation, including operations that the agent generates dynamically.

The Limits of Execution Governance for Agents

Execution governance makes the agent’s actions reviewable and bounded. It does not make them wise. An agent can use a permitted tool in a harmful way, or generate a permitted command with unintended consequences, or chain permitted operations into an outcome that no single operation would have produced.

The defense against these risks is not a tighter allowlist alone. It is a combination of sandboxing, resource limits, monitoring, human review for high-impact actions, and the principle of least privilege applied to the agent’s toolset. StackAlign contributes the execution boundary; the deployment contributes the rest.

The honest description of agent tooling on StackAlign is therefore: the agent’s execution surface is governed, the allowlist is explicit, the paths are confined, and the error contract is strict. The agent’s behavior is not guaranteed. The boundary is.

The Handoff from Training to Inference

The handoff from training to inference is where the integrity chain is most valuable and most often broken. A checkpoint that was verified during training may be copied to an inference host without verification. A converted artifact may be loaded without checking its relationship to the source checkpoint. A tokenizer may be updated without re-verifying the artifact set.

The discipline is to treat the handoff as a verification checkpoint. The artifact set is enumerated, each member is hashed, the hashes are compared against the recorded values, and the result is recorded as part of the deployment metadata. If any verification fails, the deployment is rejected.

This discipline is not exotic. It is the same pattern used in software supply chains: build, hash, record, verify before deployment. Applying it to model artifacts closes a gap that is otherwise invisible until something goes wrong.

What Safe Inference Looks Like

Safe inference, in the StackAlign sense, is inference where the artifact is verified, the execution is governed, the paths are confined, and the trust anchors are documented. It is not inference where the model is guaranteed to behave well. The first is an infrastructure property; the second is a model property. Confusing them is the most common overclaim in the field.

The integration is successful when a consumer can state both claims separately: “the inference environment is governed by StackAlign, with verified artifacts and confined execution,” and “the model’s behavior is evaluated by [separate process], with [separate evidence].” A consumer that can state only the first claim has a defensible infrastructure posture. A consumer that conflates them has neither.

Part IV — Music Production with HUSH

Chapter 8HUSH Product Family Architecture

The HUSH family is the audio-side expression of the StackAlign integration. Its architecture is a tree, not a mesh: StackAlign Baseline Clean sits at the foundation, HUSH Core consumes it as the foundation consumer for audio, and Sculptor, Observatory, and Archive consume it for their respective domains. The hush-processor and hush-core repositories are the concrete surfaces where this consumption happens.

The Tree and Why It Matters

The tree structure is the architectural expression of the dependency direction. StackAlign Baseline Clean is the root. HUSH Core is a child that consumes the root’s primitives. Sculptor, Observatory, and Archive are children that consume the same primitives, either directly or through HUSH Core’s domain interfaces.

The tree matters because it prevents the mesh failure mode. In a mesh, HUSH Core might share a path-safety helper with Sculptor, and Sculptor might share an atomic-write wrapper with Archive, and the sharing would create hidden dependencies and hidden audit surfaces. In the tree, each consumer connects to the foundation, and the foundation is the only shared security surface.

The tree also clarifies what changes when the foundation changes. A change to StackAlign’s path-safety primitive propagates to every consumer through the pinned dependency. A change to HUSH Core’s domain interfaces propagates only to the consumers that use those interfaces. The blast radius of a change is visible in the tree.

HUSH Core as Foundation Consumer

HUSH Core is the consumer that applies StackAlign’s defensive boundaries to audio-side tools. Its role is to be the domain layer where audio operations are expressed in terms of the foundation’s primitives.

Concretely, HUSH Core should route audio tool execution through sa_exec, resolve audio file paths through the path-safety primitive, write audio configuration through the atomic writer, and verify audio artifacts through the integrity primitive. It should not implement its own path resolution, its own execution wrapper, or its own atomic write. Those are foundation concerns.

The hush-core repository is the concrete surface where this contract is implemented. Its review should focus on whether every audio tool execution routes through sa_exec, whether every path operation uses the foundation’s resolution, and whether every configuration write uses the atomic writer. The review should also identify any audio-specific logic that has crept into the security layer, because that logic belongs in HUSH Core, not in StackAlign.

HUSH Processor and Real-Time Constraints

The hush-processor repository raises the hardest question in the audio integration: how do security primitives coexist with real-time constraints? Audio processing has hard deadlines, and a security check that adds latency to the audio callback is a check that will be removed under pressure.

The answer is not to skip the check. It is to place the check at the right boundary. Path resolution, execution governance, and artifact verification are setup-time concerns: they happen when the processor is initialized, when a session is loaded, or when a tool is invoked. They do not need to happen inside the audio callback. The callback should operate on already-resolved, already-verified resources.

This separation is the key to making the integration viable in real-time contexts. The processor’s initialization path uses the foundation’s primitives to resolve paths, verify artifacts, and govern tool execution. The real-time path uses the results of those checks without re-performing them. The boundary is enforced at setup, not at sample time.

The review of hush-processor should therefore focus on the boundary: are all resources resolved and verified before the real-time path begins? Is there any code path where a real-time callback performs a path resolution, an execution, or a write that should have happened at setup? A single such path is a latency hazard and a security gap.

Sculptor, Observatory, and Archive

Sculptor’s role is file and config operations and tool invocation. It is the consumer that most directly exercises the path-safety and atomic-write primitives. Its review should enumerate every file operation, every config write, and every tool invocation, and verify that each uses the foundation’s primitive.

Observatory’s role is safe inspection, analysis, and diagnostic workflows. Its characteristic risk is read-path traversal and unintended write side effects during diagnostics. Its review should focus on read confinement and on the atomicity of any diagnostic artifacts it produces.

Archive’s role is integrity, safe persistence, and recovery. It is the consumer where the residual review surfaces—history undo generation and interrupted-write recovery—matter most. Its review should trace the recovery paths and verify that history-derived paths are re-canonicalized and re-confined before application.

Each of these consumers has a distinct domain, but they share the same foundation. The tree ensures that the sharing happens at the foundation, not through cross-consumer dependencies.

The Audio QC and C++ Engine Surfaces

Audio QC and the C++ engine are the technical surfaces where the audio domain meets the foundation. Audio QC involves verifying rendered output, checking levels, detecting artifacts, and validating format compliance. The C++ engine is the low-level processing layer that performs DSP operations.

Both surfaces should consume the foundation’s primitives rather than implementing their own. Audio QC’s file reads and writes should use the path-safety and atomic-write primitives. The C++ engine’s tool invocations should route through sa_exec, and its configuration should be written atomically.

The C++ engine presents a specific challenge because C++ code often has its own path handling and its own file I/O. The integration contract requires that the engine’s I/O go through the foundation’s primitives, which may mean wrapping the engine’s I/O in a thin adapter that calls the primitives. The adapter is domain code; the primitives are foundation code. The separation should be preserved.

The Music Research Pipeline

The StackAlign Music Research pipeline is the composition of all these consumers into a research workflow. A research pipeline might ingest audio, analyze it, generate arrangements with an LLM, render output with the C++ engine, and archive the results. Each step consumes the foundation’s primitives.

The pipeline’s security posture is the composition of its steps’ postures. If the ingestion step confines paths but the rendering step writes directly, the pipeline has a gap. If the LLM step governs execution but the archiving step bypasses the atomic writer, the pipeline has a gap. The review must trace the pipeline end to end, not just each step in isolation.

This is where the tree architecture pays off. Because every step consumes the same foundation, the composition is coherent. The path-safety rules are the same at ingestion and rendering. The atomic-write protocol is the same at configuration and archiving. The integrity primitive is the same for audio artifacts and model artifacts. The pipeline is defensible because its steps share a foundation, not because each step independently invented a defense.

The Product Family as a Consumer Manifest

The HUSH product family should maintain a consumer manifest that records, for each product, which StackAlign version it consumes, which primitives it uses, and which residual review surfaces remain open. The manifest is the operational expression of the tree architecture.

A product that cannot state its pinned StackAlign version is a product whose foundation is undefined. A product that cannot state which primitives it uses is a product whose integration is unverified. A product that cannot state its open review surfaces is a product that may be overclaiming its security posture.

The manifest should travel with each release, just as the baseline’s security status travels with the baseline. The combination—pinned version, primitive usage, open surfaces—is the honest description of the product’s defensive posture.

Chapter 9HUSH Core and HUSH Processor — Defensive Audio Processing

This chapter examines the two repositories at the center of the audio integration: hush-core and hush-processor. The first is the foundation consumer for audio; the second is the real-time surface where the foundation’s setup-time checks meet the audio callback’s hard deadlines.

HUSH Core’s Contract

HUSH Core’s contract is to apply StackAlign’s defensive boundaries to audio-side tools without duplicating the foundation’s logic. In practice, this means four disciplines.

First, audio tool execution routes through sa_exec. If HUSH Core launches an audio analysis tool, a renderer, or a format converter, the launch goes through the allowlisted execution primitive. The tool’s path and arguments are resolved through the path-safety primitive before execution.

Second, audio file paths resolve through the foundation’s path-safety primitive. A path that escapes the declared audio roots is rejected, regardless of whether it is a read or a write. The resolution happens on the canonical path, after symlink and normalization resolution.

Third, audio configuration writes use the atomic writer. A configuration that controls routing, processing parameters, or session state is written through the protocol that guarantees all-or-nothing visibility. A partial configuration is a misconfigured session, and the atomic writer prevents it.

Fourth, audio artifacts are verified through the integrity primitive. A rendered file, a processed stem, or a packaged session can be hashed and checked against expected values. The trust anchor for those expected values is HUSH Core’s responsibility to document.

The hush-core repository’s review should verify each discipline and should identify any place where audio-specific logic has been substituted for a foundation primitive. A custom path resolver in HUSH Core is a fork. A raw process launch in HUSH Core is a bypass. A direct configuration write in HUSH Core is a gap.

The Setup-Time versus Real-Time Boundary

The hush-processor repository is where the setup-time versus real-time boundary is defined. The processor’s initialization phase is the place where the foundation’s primitives are applied: paths are resolved, artifacts are verified, tools are allowlisted, and configuration is loaded atomically.

The real-time phase is the place where those results are used without re-performing the checks. The audio callback operates on resolved buffers, verified samples, and loaded configuration. It does not resolve paths, launch processes, or write configuration.

This boundary is the key to making security and real-time performance compatible. A processor that performs a path resolution inside the callback has introduced a latency hazard and a potential blocking point. A processor that performs the resolution at setup and passes the result to the callback has both a security check and a predictable callback.

The review of hush-processor should trace every real-time path and verify that no foundation primitive is invoked after the real-time phase begins. The trace should include error paths: if a callback encounters a missing resource, does it resolve a path at real-time to find an alternative? If so, the boundary is broken.

Atomic Configuration in an Audio Context

Audio configuration has a property that makes atomicity especially important: a session often loads configuration incrementally. A base configuration is loaded, then a session-specific overlay, then a user override. If any of these writes is partial, the loaded configuration is a mixture of old and new state that may be internally inconsistent.

The atomic writer addresses this by ensuring that each configuration write is complete before it becomes visible. The overlay is either fully applied or fully absent. The user override is either fully present or fully absent. The loaded configuration is a coherent composition, not a partial mixture.

HUSH Core should use the atomic writer for every configuration write, including overlays and overrides. The review should verify that no configuration path bypasses the writer, and that the writer’s protocol is appropriate for the filesystem and the size of the configuration.

Integrity for Audio Artifacts

Audio artifacts—rendered files, stems, sample libraries—are large and often binary. Hashing them is straightforward, but the trust anchor problem is the same as in the LLM domain: where are the expected hashes stored, and why are they trusted?

HUSH Core should document its trust anchor for audio artifacts. Options include a manifest stored in the session directory, a hash recorded in the archive metadata, or a signed manifest from the render pipeline. The choice depends on the threat model, but the documentation is not optional. An integrity check without a stated trust anchor is a check whose value cannot be assessed.

The C++ Engine Adapter

The C++ engine is the low-level DSP layer. It likely has its own file I/O, its own path handling, and its own configuration loading. The integration contract requires that these go through the foundation’s primitives, which may require an adapter layer.

The adapter’s job is to translate the engine’s I/O requests into foundation primitive calls. A file open becomes a path resolution followed by an open within the resolved root. A configuration load becomes an atomic read of a verified file. A tool invocation becomes an sa_exec call with the engine’s arguments.

The adapter is domain code, not foundation code. It lives in HUSH Core or in the engine’s integration layer, and it calls the foundation’s primitives. It must not reimplement them. The review should verify that the adapter’s calls are the only path by which the engine reaches the filesystem or executes processes.

The Residual Surfaces in Audio Context

The baseline’s residual review surfaces—history undo generation and config atomic writer callers—have specific audio manifestations.

History undo in an audio context might mean undoing a processing step, restoring a prior session state, or reverting a configuration change. If the undo path derives file paths from stored history rather than from current configuration, those paths must be re-canonicalized and re-confined at application time. A history that was safe when recorded may not be safe when replayed.

Config atomic writer callers in an audio context include session loading, parameter changes, and preset application. Each caller must resolve its path through the path-safety primitive and use the atomic writer’s protocol. A preset application that writes directly is a gap, even if the preset is “trusted.”

The review of hush-core and hush-processor should map these residual surfaces explicitly and record their status. A surface that is mapped and reviewed is a surface that can be defended. A surface that is assumed is a surface that can be bypassed.

What the Audio Integration Demonstrates

The audio integration demonstrates that the foundation’s primitives are not specific to one domain. The same path safety, the same execution governance, the same atomic writes, and the same integrity verification that govern a server or a training pipeline also govern an audio processor. The domain supplies the resources; the foundation supplies the boundary.

It also demonstrates the cost of the integration: the setup-time versus real-time boundary must be designed, the C++ adapter must be written, and the residual surfaces must be reviewed. These costs are real, and they are the price of not duplicating security logic. The alternative—a processor with its own path handling and its own execution wrapper—would have lower upfront cost and a much higher long-term cost in audit and drift.

Chapter 10Sculptor, Observatory, Archive, and Music Research Pipelines

The remaining HUSH consumers—Sculptor, Observatory, and Archive—complete the product family. Their integration demonstrates how the foundation supports different domain roles without becoming domain-specific.

Sculptor: File, Config, and Tool Invocation

Sculptor’s domain is file and configuration operations and tool invocation. It is the consumer that most directly exercises the foundation’s path-safety, atomic-write, and execution-governance primitives.

Sculptor’s file operations should resolve paths through the foundation’s primitive before any read or write. Its configuration operations should use the atomic writer. Its tool invocations should route through sa_exec. The review should enumerate every operation and verify the primitive usage.

The characteristic Sculptor risk is the convenience path join. A path is constructed by concatenating a base directory and a user-provided name, and the result is used without canonical resolution. If the name contains traversal, the join escapes the base. The foundation’s path-safety primitive prevents this, but only if Sculptor uses it. The review should search for raw joins and replace them with the primitive.

Observatory: Safe Inspection and Diagnostics

Observatory’s domain is safe inspection, analysis, and diagnostic workflows. Its characteristic risks are read-path traversal and unintended write side effects.

Observatory’s reads should resolve paths through the foundation’s primitive and confine them to declared inspection roots. Its diagnostic artifacts should be written through the atomic writer. Its tool invocations should route through sa_exec.

The review should pay special attention to diagnostic workflows that “just read” files. A read that escapes the inspection roots is a traversal, and it can expose data that the diagnostic was never meant to access. The foundation’s path-safety primitive makes the escape visible by rejecting it.

Archive: Integrity, Persistence, and Recovery

Archive’s domain is integrity, safe persistence, and recovery. It is the consumer where the foundation’s integrity primitive and atomic-write primitive are most heavily used, and where the residual review surfaces matter most.

Archive’s persistence should use the atomic writer for every write. Its artifacts should be hashed and verified against a documented trust anchor. Its recovery paths should re-canonicalize history-derived paths and confine them before application.

The review should trace Archive’s recovery behavior end to end. What happens when a write is interrupted? What happens when a hash verification fails? What happens when a history undo references a path that no longer exists or now resolves outside the roots? Each of these is a recovery scenario, and each should have a defined, reviewed behavior.

The Music Research Pipeline as a Composition

The StackAlign Music Research pipeline composes these consumers into a workflow: ingest audio, analyze it with Observatory, sculpt it with Sculptor, generate arrangements with LLM tooling, render with the C++ engine, archive the results with Archive.

The pipeline’s security posture is the composition of its steps. If each step consumes the foundation’s primitives, the composition is coherent. If any step bypasses a primitive, the pipeline has a gap that the other steps cannot compensate for.

The review should trace a sample through the pipeline and verify the primitives at each handoff. Ingestion resolves and confines the input path. Analysis reads within the inspection roots. Sculpting writes configuration atomically and invokes tools through sa_exec. LLM tooling governs execution and verifies artifacts. Rendering uses setup-time resolution. Archiving hashes and persists atomically. The trace should identify every handoff and every primitive invocation, and it should flag any handoff where the primitive is absent.

The Consumer Manifest for HUSH

Each HUSH product should have a consumer manifest entry that records:

  • the pinned StackAlign version;
  • the primitives used (path safety, sa_exec, atomic writer, integrity);
  • the declared roots and allowlists;
  • the trust anchor for expected hashes;
  • the residual review surfaces that remain open;
  • the validation evidence reference.

The manifest is the operational summary of the integration. It allows a reviewer to assess the product’s posture without reading the entire codebase, and it allows an operator to know which version of the foundation is deployed.

The Composition Argument

The HUSH product family is the strongest argument for the foundation approach. Four consumers with different domains—audio processing, file and config operations, inspection and diagnostics, integrity and recovery—share the same primitives and the same review discipline. The foundation is audited once, and the consumers inherit the audit.

The alternative—four consumers with four private security implementations—would produce four audit surfaces, four sets of drift, and four opportunities for a bypass. The foundation approach does not eliminate the need for consumer review; it eliminates the need for consumer security invention. The consumers review their domain behavior and their primitive usage. They do not review their own path-safety implementation, because they do not have one.

The Limits of the Audio Integration

The audio integration does not make audio processing safe in a general sense. It makes the execution, path, write, and integrity surfaces governable. It does not address plugin sandboxing, real-time thread safety in the DSP code, numerical stability, or the many domain-specific hazards of audio software.

Those hazards are real, and they belong to the audio domain. The foundation’s contribution is to ensure that the audio domain’s security logic is not duplicated and not bypassed. It is a foundation, not a complete security program.

Part V — Operations

Chapter 11Disposable EL9 Validation and Evidence

The transition from static review to runtime clearance is the most important gate in the integration. It is also the gate most likely to be skipped under schedule pressure. This chapter defines the validation work that must happen on a disposable Enterprise Linux 9 environment and the evidence that must be produced before the baseline can be described as runtime-validated.

Why Disposable EL9

Validation must run on a disposable Enterprise Linux 9 environment because the goal is to observe runtime behavior without risking production state. A disposable environment can be reset to a known state between tests, which is essential for reproducing failures and for ensuring that one test’s side effects do not contaminate the next.

EL9 is the target because the baseline’s runtime behavior depends on the operating system’s filesystem semantics, process model, and security controls. Validation on a different distribution would not establish the properties that matter for the EL9 deployment. The environment should be documented by image identifier so that the validation is reproducible.

The Test Matrix

The test matrix should cover the baseline’s primitives and the residual review surfaces. At minimum, it should include:

Expected allowed operations. Audio tool execution through sa_exec with permitted paths. Configuration writes through the atomic writer. Artifact verification with matching hashes. These tests confirm that the primitives work on the happy path.

Rejected operations. Execution of a non-allowlisted program. Path resolution outside the declared roots. Artifact verification with a mismatched hash. These tests confirm that the rejection behavior is correct and that the error contract is honored.

Malformed input. Paths with traversal sequences, symbolic links that escape roots, Unicode normalization edge cases, and arguments that attempt to inject additional commands. These tests confirm that the path-safety primitive handles adversarial input.

Rollback and interrupted writes. A write that is interrupted before completion should leave the prior state intact. A rollback should restore the prior state without partial artifacts. These tests confirm the atomic-write protocol.

Permission boundaries. Operations that require elevated privilege should be reachable only through the reviewed chain. Operations that do not require elevation should fail cleanly if attempted with elevation. These tests confirm the privilege model.

Recovery behavior. After an interrupted write or a failed verification, the system should recover to a defined state. The recovery should be documented and reproducible.

History undo. A history undo that references a path should re-canonicalize and re-confine the path before application. A history undo that references a path outside the roots should be rejected.

Config atomic writer callers. Every caller should be exercised, and the write pattern should be verified against the atomic protocol. A caller that writes directly should be identified and corrected.

The Root-Apply Chain Validation

The root-apply chain requires specific validation because it is the least concretely established part of the baseline. The validation should map the chain from each elevated operation backward to its callers and forward from sa_exec to the operations it can reach. Each point of elevation should be identified, and each input that influences the elevated operation should be traced.

The validation should include tests that attempt to reach elevated operations through paths that are not the reviewed chain. If such a path exists, the chain is not complete, and the baseline’s claim that privileged execution is governed is not yet established.

The Evidence Bundle

The evidence bundle is the artifact that supports the runtime-clearance claim. It should include:

  • the EL9 image identifier;
  • the baseline commit hash;
  • the test commands and their full output;
  • the pass/fail results for each test;
  • the failures and their root causes;
  • the unresolved items and their status;
  • the reviewer sign-off.

The bundle should be versioned and stored alongside the baseline tag. A runtime-clearance claim without a bundle is an assertion without evidence. A bundle without a reviewer sign-off is a test run without a judgment.

The Promotion Sequence

The promotion sequence follows from the evidence. First, complete the repository inspection and close K4 or document the remaining blockers. Second, run the disposable EL9 validation. Third, publish the evidence bundle. Fourth, freeze and tag the verified baseline. Fifth, integrate the pinned baseline into the HUSH shared tooling layer. Sixth, add model-creation tooling as a separate consumer. Seventh, require downstream consumers to inherit the baseline rather than duplicating its logic.

Each step is gated by the previous one. The baseline is not tagged before validation. The consumers do not integrate before the tag. The model-creation integration does not proceed before the HUSH integration is stable. The sequence is deliberately conservative because the cost of a premature clearance claim is higher than the cost of a delayed integration.

What Runtime Clearance Means

Runtime clearance means that the baseline’s primitives have been exercised in a representative environment and have behaved as designed. It does not mean that the baseline is free of vulnerabilities. It does not mean that every consumer’s integration is correct. It does not mean that the deployment is secure.

It means that the specific claims in the baseline’s documentation—path safety, execution governance, atomic writes, integrity verification—have been tested and observed. The claim is narrower than “secure,” and it is more useful because it is specific.

The Evidence as a Living Artifact

The evidence bundle should not be a one-time artifact. It should be updated as the baseline changes and as new residual surfaces are identified. A baseline that was cleared at one commit and has since changed is a baseline whose clearance is stale. The consumer manifest should reference the evidence for the exact pinned version, not for the baseline in general.

This discipline keeps the clearance honest. A claim of runtime clearance is a claim about a specific version, in a specific environment, with specific evidence. When any of those change, the claim must be re-established.

Chapter 12Consumer Integration and Long-Term Operations

The final chapter addresses the operational discipline that sustains the integration: version pinning, consumer manifests, incident response, rollback, and the long-term boundary between the foundation and the model-creation domain.

Version Pinning and the Consumer Manifest

Consumers must pin the baseline to a commit or tag, never to a branch. A branch is a moving target; a tag is a fixed reference. The consumer manifest records the pinned version and the evidence bundle that supports it.

The pin should be updated deliberately, with a review of the baseline’s changes and a re-run of the relevant validation tests. A consumer that updates the pin without reviewing the changes has lost the benefit of the versioning discipline.

Incident Response and Rollback

An incident in a consumer may originate in the consumer’s domain logic, in the foundation, or in the integration. The response should distinguish these cases. If the incident is in the foundation, the fix is applied upstream and a new baseline version is tagged and validated. If the incident is in the consumer’s domain logic, the fix is applied in the consumer. If the incident is in the integration—a primitive used incorrectly, a path resolved incorrectly—the fix is in the consumer’s usage of the primitive.

Rollback follows the same structure. A consumer that needs to roll back a baseline update should pin to the prior validated version and re-run the integration tests. The rollback should be rehearsed, not improvised.

The Boundary with Model Creation

The boundary between the foundation and model creation must be maintained over time. StackAlign should not absorb model-specific logic, and model-creation tooling should not fork the foundation’s primitives.

This boundary is tested whenever a model-creation need seems to require a foundation change. The correct response is to ask whether the need is domain-agnostic. If it is, it may belong in the foundation. If it is model-specific, it belongs in the model-creation layer, consuming the foundation’s primitives. The distinction prevents the foundation from becoming a model framework and prevents the model layer from becoming a security fork.

The Long-Term Audit Surface

The long-term audit surface is the set of places where the integration can fail: the foundation’s primitives, the consumer’s domain logic, the handoffs between them, and the residual review surfaces. The consumer manifest should enumerate this surface, and the review process should revisit it periodically.

A periodic review should ask: are there new raw executions that bypass sa_exec? Are there new direct writes that bypass the atomic writer? Are there new path joins that bypass the path-safety primitive? Are the trust anchors for expected hashes still valid? Are the residual surfaces still open, and if so, why?

The Acceptance Criteria

The integration is integration-ready when the following are true:

  • K4 is closed, or the remaining blockers are documented and accepted.
  • History undo and config atomic writer call sites are reviewed.
  • The root-apply chain is established or explicitly blocked.
  • EL9 validation evidence is recorded.
  • The baseline is tagged.
  • Consumer manifests pin the tag.
  • No product duplicates the foundation’s security primitives.
  • Documentation states static review versus runtime clearance accurately.

These criteria are not a finish line. They are the minimum conditions under which the foundation can be consumed without misrepresentation. The integration continues after they are met, with periodic review and revalidation.

The Final Claim

The final claim is deliberately modest: StackAlign provides a shared defensive foundation for base servers, LLM creation, and music production, and the HUSH product family demonstrates how that foundation can be consumed across domains without duplicating security logic.

The foundation is statically reviewed and not yet runtime-cleared. The K4 migration is open. The residual surfaces are open. The root-apply chain is not concretely established. EL9 validation is pending.

Those facts do not diminish the foundation’s value. They define the work that remains. A foundation that is honestly incomplete is more useful than a foundation that is prematurely declared complete, because the honest foundation can be finished, and the premature claim cannot be trusted.

The StackAlign Music Research stack is a promising defensive composition. It becomes an integration-ready system when the gates in this book are satisfied and the evidence is published. Until then, the correct description is the one the audit gave: a promising defensive baseline, not yet runtime-cleared.
